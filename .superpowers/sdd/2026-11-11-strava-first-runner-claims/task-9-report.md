# Task 9 report

Replaced the runner Wrapped endpoint with `getStravaWrappedForUser(userId, runnerId)`. The read starts at the user's direct `runner_access` row and loads registration identity from the related runner, category, and event. An organizer with event access alone gets the same private 404 as a missing runner. Each success and handled error sends `Cache-Control: private, no-store`.

## Contract and privacy review

- `setup_required`, `authorizing`, `importing`, `no_match`, `building`, `failed`, and `reauth_required` each return exactly `{ state, registration }`. Registration contains `runner: { id, name, bibNumber }` and `event: { name, date, category }`.
- `needs_confirmation` adds only `candidates`. Each candidate contains `activityId`, `startTimeLocal`, `distanceMeters`, `sportType`, `gpsAvailable`, and `matchReason`. The candidate row and its normalized Run are scoped by user, generation, and registration. The existing safe projector verifies athlete ownership and replaces unknown reasons with a generic confirmation reason. Candidate IDs appear only in this owner-only state.
- `ready` adds only `snapshot` and `photos`. The selected V1 build must be ready, match the registration ID, and pass the exact Task 8 validator, including its nested allowlists. The stored projection remains intact. The separate registration field supplies current display identity. Photos match the current BIB and use the six existing photo fields. Missing, rejected, or stalled photo reads return an empty array, and a changed BIB drops the old photo list.
- Connection reads select lifecycle fields without reading credentials. Import work is scoped to the current attachment incarnation. Runnable imports take precedence over older failed work. A selection with no V1 snapshot is building. A failed build or invalid ready projection returns generic `failed` without internal errors. Before returning a snapshot or candidates, the service rechecks direct ownership, connection generation and athlete, attachment incarnation, selection, and build identity and status. These are sequential API reads with a final recheck, so they do not supply a single database transaction snapshot.
- The service has no path to the chip controller, live enrichment, or the Strava provider. Share and PNG export require a ready V1 snapshot. They use Strava distance, moving time, average pace, and kilometer split pace. The share model carries all formatted splits. The PNG shows up to six splits and says how many it shows when more are present. Missing split and pace data have explicit absence copy. Tests assert that rendered output contains no chip rank, percentile, overtakes, chip time, coordinates, provider activity or athlete identifiers, or health metrics. The non-health decision in SRS v4 FR-14 already covers this behavior.
